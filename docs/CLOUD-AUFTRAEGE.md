# Cloud-Auftrag: alles Fertigbauen in einer Sitzung

Erste Nachricht an die Cloud-Sitzung: `Lies docs/CLOUD-AUFTRAEGE.md und baue alles darin fertig.`

## Ausgangslage (Stand 2.11.2026)

Auf `main` liegen fertig und geprüft: `packages/rules` (Regel-Engine, 28 Tests), `apps/api` (Backend, 37 Tests, Mail mit PDF nachgewiesen), `apps/mobile` (Expo-App; Typecheck, Lint, Expo-Doctor, Android-Export grün). Unfertig: `apps/web` (angefangenes Next.js-Gerüst mit Teilen von Assistent, Chat, Admin, ungetestet). Noch nicht vorhanden: Deployment und Betriebsanleitung.

Grundlagen im Repository: `docs/ARCHITEKTUR.md` (verbindlicher Vertrag: API-Endpunkte, Typen, Datenmodell, Env-Variablen, Farben, Grundsätze), `docs/RECHERCHE.md` (Betreiberdaten, Design-Vorbilder, Recht, Sicherheit), `docs/DESIGN-RICHTUNG.md` (Vorbild lusion.co in zehn Kapiteln, Mini-Clips, Technik), `docs/design/*.dc.html` (fertige Entwürfe: `Main.dc.html` Startseite Desktop, `Mobile.dc.html` Handy, `Clip-Ablauf`, `Clip-Platte`, `Clip-Wege` als animierte CSS/SVG-Schleifen mit exakten Keyframes, Farben, Texten), `README.md`, `.env.example`. API-Routen: `apps/api/src/routes/public.ts`, `apps/api/src/routes/admin.ts`.

Regeln: zuerst `git pull origin main`. Arbeite auf Branch `feat/fertigstellung`, committe in sinnvollen Schritten, pushe, öffne am Ende EINEN Pull Request gegen main mit Abschlussbericht (gebaut, geprüft mit Ergebnis, offen). Keine Secrets ins Repository, keine erfundenen Preise oder Produktdaten (Platzhalter bleiben markiert), keine weiteren Sitzungen starten. Fertige Teile (`packages/rules`, `apps/api`, `apps/mobile`) nur ändern, wenn die Integration es zwingend verlangt, und dann im Bericht nennen.

API lokal starten: `npm --prefix packages/rules install && npm --prefix packages/rules run build && npm --prefix apps/api install && cd apps/api && npm run db:setup && npm run dev` (Port 4000; Env `SESSION_SECRET`, `ADMIN_EMAIL`, `ADMIN_PASSWORD` setzen; ohne `ANTHROPIC_API_KEY` antwortet die KI mit Vorlagen). Test-Mailserver: `npx maildev --smtp 1025 --web 1080`.

## Teil 2: Deployment, Server-Setup, Betrieb

Neu anlegen: `deploy/`, `docker-compose.yml` und `docker-compose.dev.yml` im Root, `apps/api/Dockerfile` + `.dockerignore`, `apps/web/Dockerfile` + `.dockerignore`, `.github/workflows/deploy.yml`, `docs/BETRIEB.md`.

1. Dockerfiles (Multi-Stage, node:24-alpine): API baut zuerst `packages/rules`, dann Prisma generate und Build, Start per Skript aus `apps/api/package.json`, Volume für `apps/api/data`; Web als Next.js standalone mit `API_INTERNAL_URL=http://api:4000`.
2. `docker-compose.yml` (Produktion: `api`, `web`, `caddy` mit automatischem Let’s Encrypt; Volumes `api_data`, `caddy_data`; Healthchecks `/api/health` und `/`; Restart-Policy; Env aus `.env`), `docker-compose.dev.yml` mit MailDev.
3. `deploy/Caddyfile` (Domain aus `DOMAIN`, `/api/*` zur API, Rest zum Web, Security-Header; optional IP-Allowlist für `/admin*` aus `ADMIN_ALLOW_IPS`), `deploy/setup-server.sh` (idempotent, Ubuntu 24.04: Docker, ufw 22/80/443, unattended-upgrades, Nutzer, `/opt/bodenschutz`, Repo klonen, `.env` aus Vorlage mit zufälligem SESSION_SECRET und Rechten 600, `docker compose up -d`), `deploy/backup.sh` (SQLite sicher sichern, Uploads und PDFs als tar.gz, 14 Tage Rotation, optional rclone), `deploy/restore.sh`, `deploy/update.sh` (pull, build, up, `prisma db push` im API-Container, Smoke-Test `/api/health`), `deploy/cron.example` (Backup täglich 03:00).
4. `.github/workflows/deploy.yml`: bei Tag `v*` Images nach `ghcr.io/cykruz/bodenschutz-api` und `ghcr.io/cykruz/bodenschutz-web`; optionaler SSH-Deploy-Job mit Secrets `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_SSH_KEY`, nur aktiv wenn gesetzt.
5. `docs/BETRIEB.md` auf Deutsch: Teil für den Techniker (Server 2 vCPU/4 GB/40 GB, DNS für bodenschutz-austria.at und www, Setup-Skript, `.env` ausfüllen mit ANTHROPIC_API_KEY, SMTP und IMAP für Marios Postfach, ADMIN_*, erster Start, Admin-Login, Backups, Updates, Logs, häufige Fehler) und Teil für Mario in einfacher Sprache (was läuft wo, Login in die Verwaltung, was tun wenn etwas nicht geht, Datensicherung). Checkliste „Vor dem Livegang“: Impressum vollständig, Datenschutz mit KI-Abschnitt, Platzhalterdaten ersetzt und bestätigt, Auto-Versand aus, Test-Anfrage von Website und App, Postfach-Test, Backup-Test, HTTPS-Test.
6. Sicherheit: Container ohne Root, nur nötige Ports, `.env` 600, Fail2ban-Hinweis, Secrets nie im Image.

Prüfen: `docker compose config` fehlerfrei; beide Images bauen und mit `docker-compose.dev.yml` starten, Healthchecks grün, Anfrage über die containerisierte Website bis zur Mail in MailDev; `shellcheck` und `bash -n` auf alle Skripte.
