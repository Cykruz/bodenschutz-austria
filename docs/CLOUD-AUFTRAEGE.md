# Cloud-Aufträge

Stand 2.11.2026. Zwei Aufträge sind offen und laufen parallel in je einer eigenen Cloud-Sitzung. Jede Sitzung bekommt als erste Nachricht genau einen Satz:

- Sitzung Website: `Lies docs/CLOUD-AUFTRAEGE.md und mache ausschließlich Auftrag A (Website).`
- Sitzung Deployment: `Lies docs/CLOUD-AUFTRAEGE.md und mache ausschließlich Auftrag B (Deployment).`

| Teil | Ordner | Stand |
|---|---|---|
| Regel-Engine | `packages/rules` | fertig auf main, 28 Tests grün |
| Backend-API | `apps/api` | fertig auf main, 37 Tests grün, Mail mit PDF geprüft |
| Expo-App | `apps/mobile` | fertig auf main, Typecheck, Lint, Expo-Doctor, Android-Export grün |
| Website | `apps/web` | **Auftrag A, offen.** Auf main liegt ein angefangener Stand (Next.js-Gerüst, Teile von Assistent, Chat, Admin), ungetestet |
| Deployment | `deploy/`, Dockerfiles, `docs/BETRIEB.md` | **Auftrag B, offen** |

Regeln für beide: zuerst `git pull origin main`; nur die eigenen Ordner ändern; eigener Branch; am Ende Pull Request gegen main mit Abschlussbericht (gebaut, geprüft mit Ergebnis, offen); keine Secrets ins Repository; keine erfundenen Preise oder Produktdaten; keine weiteren Sitzungen starten.

Grundlagen (im Repository): `docs/ARCHITEKTUR.md` (verbindlicher Vertrag: alle API-Endpunkte, Typen, Datenmodell, Env-Variablen, Farben, Grundsätze), `docs/RECHERCHE.md` (Betreiberdaten, Design-Vorbilder, Recht, Sicherheit), `docs/DESIGN-RICHTUNG.md` (Vorbild lusion.co in zehn Kapiteln, Mini-Clips, Technik), `docs/design/*.dc.html` (fertige Design-Entwürfe: `Main.dc.html` Startseite Desktop, `Mobile.dc.html` Handy, `Clip-Ablauf`, `Clip-Platte`, `Clip-Wege` als animierte CSS/SVG-Schleifen mit exakten Keyframes, Farben und Texten), `README.md`, `.env.example`. Die API ist fertig: ihre Routen stehen in `apps/api/src/routes/public.ts` und `apps/api/src/routes/admin.ts`, sie läuft mit `npm --prefix packages/rules install && npm --prefix packages/rules run build && npm --prefix apps/api install && cd apps/api && npm run db:setup && npm run dev` auf Port 4000 (Env: `SESSION_SECRET`, `ADMIN_EMAIL`, `ADMIN_PASSWORD` setzen; ohne `ANTHROPIC_API_KEY` antwortet die KI mit Vorlagen).

## Auftrag B: Deployment, Server-Setup, Betrieb (Branch `feat/deploy`)

Ziel: alles für den Livebetrieb auf einem eigenen Linux-Server. Nur ändern: neuer Ordner `deploy/`, `docker-compose.yml` und `docker-compose.dev.yml` im Root, `apps/api/Dockerfile` + `.dockerignore`, `apps/web/Dockerfile` + `.dockerignore`, `.github/workflows/deploy.yml`, `docs/BETRIEB.md`. `ci.yml` nicht anfassen.

1. Dockerfiles (Multi-Stage, node:24-alpine): API baut zuerst `packages/rules`, dann Prisma generate und Build, Start per Skript aus `apps/api/package.json`, Volume für `apps/api/data`; Web als Next.js standalone mit `API_INTERNAL_URL=http://api:4000` (Web ist noch im Bau: Dockerfile gegen die Standard-Next-Struktur mit `output: 'standalone'` schreiben und im PR vermerken, dass `next.config.ts` diese Option braucht).
2. `docker-compose.yml` (Produktion: `api`, `web`, `caddy` mit automatischem Let’s Encrypt; Volumes `api_data`, `caddy_data`; Healthchecks `/api/health` und `/`; Restart-Policy; Env aus `.env`), `docker-compose.dev.yml` mit MailDev.
3. `deploy/Caddyfile` (Domain aus `DOMAIN`, `/api/*` zur API, Rest zum Web, Security-Header HSTS, X-Content-Type-Options, Referrer-Policy, Permissions-Policy; optional IP-Allowlist für `/admin*` aus `ADMIN_ALLOW_IPS`), `deploy/setup-server.sh` (idempotent, Ubuntu 24.04: Docker, ufw 22/80/443, unattended-upgrades, Nutzer, `/opt/bodenschutz`, Repo klonen, `.env` aus Vorlage mit zufälligem SESSION_SECRET und Rechten 600, `docker compose up -d`), `deploy/backup.sh` (SQLite sicher sichern, Uploads und PDFs als tar.gz, 14 Tage Rotation, optional rclone-Ziel), `deploy/restore.sh`, `deploy/update.sh` (pull, build, up, `prisma db push` im API-Container, Smoke-Test `/api/health`), `deploy/cron.example` (Backup täglich 03:00), `deploy/nginx/` als dokumentierte Alternative.
4. `.github/workflows/deploy.yml`: bei Tag `v*` Images bauen und nach `ghcr.io/cykruz/bodenschutz-api` und `ghcr.io/cykruz/bodenschutz-web` pushen; optionaler SSH-Deploy-Job mit Secrets `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_SSH_KEY`, nur aktiv wenn gesetzt.
5. `docs/BETRIEB.md` auf Deutsch: Teil für den Techniker (Server 2 vCPU/4 GB/40 GB, DNS für bodenschutz-austria.at und www, Setup-Skript, `.env` ausfüllen mit ANTHROPIC_API_KEY, SMTP und IMAP für Marios Postfach, ADMIN_*, erster Start, Admin-Login, Backups prüfen, Updates, Logs, häufige Fehler) und Teil für Mario in einfacher Sprache (was läuft wo, Login in die Verwaltung, was tun wenn etwas nicht geht, wen anrufen, Datensicherung). Checkliste „Vor dem Livegang“: Impressum vollständig, Datenschutz mit KI-Abschnitt, Platzhalterdaten ersetzt und bestätigt, Auto-Versand aus, Test-Anfrage von Website und App, Postfach-Test, Backup-Test, HTTPS-Test.

**Prüfen:** `docker compose config` fehlerfrei; API-Image bauen und starten, Healthcheck grün; Web-Image bauen sobald `apps/web` auf main baubar ist, sonst im Bericht als offen vermerken; `shellcheck` und `bash -n` auf alle Skripte.
